A Data Model for CCF and PCF Calculation

Corporate and Product Carbon Footprint numbers are usually presented as if they're the same calculation at different scales. They're not — the point where they diverge is the part worth designing carefully.

The mechanism

Both CCF and PCF start from the same two inputs — activity data pulled from ERP systems, and an emission factor matched to that activity — and run through the same calculation step. They only diverge at the last hop: CCF sums the results; PCF allocates them to a single product using a chosen allocation key. That fork is the part a data model has to get right, because it's a methodology decision, not an arithmetic one.

Why the fork matters

It's tempting to treat PCF as "CCF divided by units produced." That only works if a single product consumes a company's entire footprint — true for a single-product factory, false almost everywhere else. In practice, shared emissions (a shared production line, shared logistics, corporate overhead) have to be allocated down to one product using a defensible key: production volume, revenue share, or mass — each of which produces a different PCF for the same product. The allocation key isn't a technical detail the engineering team picks; it's a methodology decision with real disclosure consequences, and the data model needs to keep it visible and swappable, not buried in a calculation nobody can re-derive.

Why the factor library is versioned, not static

A calculation engine that looks up "today's" emission factor will silently misstate history the moment a factor is updated — recalculating a 2024 activity with a 2026 factor produces a number that was never true. Emission factors need a validity window (valid_from / valid_to), and the calculation engine has to match on the activity's date, not the calculation's run date. This is the same failure mode as hardcoding a regulatory threshold instead of dating it — see what sustainability regulations actually require of software products.
